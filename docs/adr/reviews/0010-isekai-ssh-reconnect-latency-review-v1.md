## 1. 問い(2)への回答: 施策Cは短い断では体験を悪化させる(Y1、Blocking)

### 1.1 断の長さで場合分けする

ゲートは`Down`という**レベル**だけを見て無条件に`Rejected`を返す。
しかし結果は、断がどれだけ続くかで正反対になる。

**ケース1: 断が30秒未満(=`HELLO_ACK_TIMEOUT`より短い)**

- **今日**: クライアントBはmuxハンドシェイクに入り、ownerの
  `channel_open_session`が輸送層のresume完了とともに**成功する**。
  例えば断が20秒なら、Bは20秒後に`HelloAck`を受け取り、
  **多重化されたセッションを得て正常に動く**(クライアント側の
  上限は30秒なのでまだ余裕がある)。ユーザーから見れば
  「少し待たされたが、いつも通り繋がった」。
- **施策C導入後**: Bは`t=0`で即座に`Rejected`を受け、直接接続へ
  フォールバックする。その直接接続は**新しい`isekai-pipe connect`子を
  起こして、まだ壊れているネットワーク上でゼロからダイヤルする**
  ——既存のresume中セッションの恩恵を一切受けられない。
  実インシデントのタイムラインが示す通り、この経路は
  「ダイヤル失敗 → `ConnectOutcome` → 再bootstrap判断 → サイレント
  再デプロイ」で**数十秒かかる**(08:46:01→08:46:47で約46秒)。
  しかも成功しても**多重化は失われる**。

⇒ **このケースでは施策Cは純粋な劣化である。** 20秒で多重化付きで
繋がっていたものが、46秒以上かかって多重化なしで繋がる。

**ケース2: 断が30秒以上**

- **今日**: Bは30秒待って`Rejected`、そこから直接接続。
- **施策C導入後**: Bは即座に`Rejected`、そこから直接接続。
  **30秒得をする。** これがADRの想定しているケース。

### 1.2 どちらのケースが一般的かは、このリポジトリ自身が答えを持っている

`isekai-pipe/src/resume_loop.rs:81`の`RECONNECT_NOTIFY_GRACE`(15秒)の
docは、`tssh`の`kDefaultUdpReconnectTimeout`に合わせた理由として
**「15秒未満の断は自己修復するのが当たり前なので、ユーザーに通知すら
しない」**という設計判断を明記している。つまりこのコードベースは
**「短い断のほうが一般的」という前提で設計されている**。

さらに`RESUME_BACKOFF`(初期500ms・上限10秒)から見ても、
resumeは通常**数秒で完了する**ことが期待されている。

⇒ **ゲートが発火する`Down`区間の大半は、ケース1(30秒未満)である
可能性が高い。** 施策Cは、頻度の高いケースを悪化させて、
頻度の低いケースを改善する設計になっている。

### 1.3 より本質的な問題: 待ち方針の所在(SSOT的な観点)

「どれだけ待つか」という方針は、**既にクライアント側が持っている**
——`HELLO_ACK_TIMEOUT`(30秒、`client.rs:47-66`)がまさにそれで、
docにも「オーナー側の正当な仕事は数秒かかりうるので、owner側の
`HELLO_READ_TIMEOUT`(10秒)より意図的に寛容にした」と、
**方針として選ばれた値であること**が書かれている。

施策Cのゲートは、この方針を**ownerが横取りして「0秒で諦めろ」に
書き換える**ものである。ownerはそのクライアントが
多重化をどれだけ重視しているか、あとどれくらい待てるかを知らない。
`.claude/rules/rust-ssot.md`の精神(判断は正しい所有者に置く)に
照らすと、**これは方向が逆**である。

### 1.4 取りうる設計(いずれもゲートの利点を保ちつつケース1を壊さない)

- **(α) 情報を渡すだけにする(推奨)**: ゲートで`Rejected`を返す代わりに、
  **`Frame`で「輸送層が再接続中(N秒経過、resume windowはあとM秒)」を
  クライアントへ伝え、待ち方針はクライアントに委ねる**。
  クライアントは今日通り`HELLO_ACK_TIMEOUT`まで待ち、
  **その間その情報を画面/タイトルに出せる**(§3.4の進捗表示が
  推測ではなく実データになる、という施策Cの利点はそのまま得られる)。
  ケース1では今日通り成功し、ケース2では今日通り30秒後に
  フォールバックする——**悪化する経路が1つも無い**。
  代償は「ケース2での30秒短縮」を諦めること。
  (プロトコル追加が要るが、これは第2回で代案Eとして記録した
  `HelloProgress`フレームそのもの。ゲートと同じ情報を運ぶだけなので、
  施策Bの成果は完全に活きる。)
- **(β) 断の経過時間で条件づける**: `now - since >= HELLO_ACK_TIMEOUT`の
  ときだけ`Rejected`を返す。「**クライアントが待つつもりの時間より
  長く既に落ちているなら、待たせても無駄**」という、**新しい定数を
  1つも導入しない**判断規則になる(使うのは輸送層が報告した事実
  `since`と、既存の`HELLO_ACK_TIMEOUT`だけ)。ケース1では素通しになり、
  ケース2では即座に弾ける。**(α)より実装が軽い。**
  ただし「30秒落ちていた直後に回復する」ケースでは(α)より劣る。
- **(γ) 現状のまま(無条件`Rejected`)**: ケース1を悪化させる。
  採るなら、**§5.4に「短い断ではmuxの成功経路を捨てる劣化がある」と
  明記**し、その上で意図的な選択であることを書く必要がある。

**推奨は(β)**——新しい定数を導入せず、ADRの「生死の推定に時間閾値を
持ち込まない」という原則とも整合する(`since`は推定ではなく
輸送層が宣言した事実、`HELLO_ACK_TIMEOUT`は既存のクライアント側方針)。
より丁寧にやるなら(α)。

## 2. 問い(1)への回答: 施策Aの残る根拠も崩れている(Y2、Blocking)

### 2.1 F1の飢餓には、観測可能な帰結がほぼ無い

§3.1のF1は「ハング中は`handle_died`の1秒ポーリングが評価されないので、
holderが終了できる唯一の経路がkeepalive死(実効300秒)に縮退する」と
(N1の訂正後は正しく)書いている。しかし**その300秒の時点で何が起きるかを
最後まで追うと、施策Aの有無で差が出ない**:

russhのセッションタスク(`run_inner`)が終了すると、`Session`構造体が
dropされ、**同時に**次の2つが起きる:

1. `self.receiver`(`Handle::sender`の相手)がdropされる →
   **`Handle::is_closed()`が`true`になる**(`client/mod.rs:236-238`)
2. `self.channels`(各チャネルのsender)がdropされる →
   詰まっていた`wait_channel_confirmation`の`receiver.recv()`が`None`を
   返し、**`channel_open_session`が`Err(Disconnect)`で返る**
   (`client/mod.rs:453-461`)

つまり**`handle_died`が検知したい事象と、ハングを解く事象は同一**である。
そして今日のコードでは、2の`Err`が返った瞬間に:

- `owner.rs:366`のguardが解放され、
- `open_result`の`Err`アーム(`owner.rs:400-413`)が
  **`shutdown.notify_waiters()`を呼び**、
- `serve_clients`の`shutdown`ブランチ(`owner.rs:225-232`)が
  **即座にholderを終了させる**

——`handle_died`の1秒ポーリングを**待つまでもなく**holderは畳まれる。
むしろ`shutdown`経路のほうが速い(ADR §1.2が引用している通り、
実インシデントの08:48:17で実際に機能したのもこの経路である)。

⇒ **施策Aを入れても入れなくても、holderが終了する時刻は同じ。**
F1は「`handle_died`が評価されない」という**機構としては実在する**が、
**それによって遅れるものが無い**。

### 2.2 したがって「施策Cの前提条件」という位置づけも成立しない

§3.1施策Cは「施策Aで`handle_died`の飢餓が消えるので、
輸送層が諦める → 子が終了 → `is_closed()`が`true` → `handle_died`が
発火 → holderが即座に終了、という経路が1秒程度で機能するようになる」と
書いている。しかし§2.1の通り、**子の終了もまた同じ単一イベント**
(stdio EOF → セッションタスク終了 → sender/channelsが同時にdrop)であり、
ハング中のクライアントが居れば`Err`経路が、居なければ`handle_died`が、
どちらにせよ即座に発火する。**施策Aは不要**。

### 2.3 施策Aに残る、本当の(しかし狭い)価値

公平を期すため、施策Aで実際に改善するものを列挙する:

1. **`relay_loop`の生死確認(`owner.rs:845`)の巻き添え解消**:
   確立済みクライアントのowner側teardownが、新規クライアントのハングで
   ブロックされなくなる。これにより`active_clients`が正しく減算され、
   `IDLE_GRACE`が機能する。**ただし**、その状況(全クライアントが去り、
   ハング中のクライアントだけが残る)はハング中のクライアント自身が
   `active_clients`を掴んだままなので、結局`IDLE_GRACE`は発火しない
   ——**効果はさらに限定的**。
2. **健全なリンクで複数タブが同時に開くときの直列化の解消**:
   健全時の`channel_open_session`は数十ms程度なので、
   体感差はほぼ無い。
3. **構造的な正しさ**: `Mutex`は実際に過剰であり、`RwLock`のほうが
   russhのAPIを正しく反映している(これは真)。

対して施策Aが**新たに持ち込む**もの:

- `NativeHandle: Sync`という新しい境界(未検証、外れたら代替なし)
- `LOCK_BUDGET`という新しい定数と、writer starvation という新しい失敗モード
  (X2: 最悪 N×`LOCK_BUDGET`)
- 未確認のまま同時in-flightなオープンが1件からN件へ(X3:
  回復時の`MaxSessions`超過でholderが畳まれうる)
- 呼び出し6箇所+シグネチャ6種+テストの変更

**結論**: 「バグ修正」としては正当化できない(直る観測可能な不具合が
ほぼ無い)。「構造的な正しさの整理(リファクタ)」としてなら妥当だが、
その場合は:

- **§7手順1から外し**、施策B/Cとは独立した小さなクリーンアップとして
  別PRに切り出す
- **実機で効果を測る対象にしない**(測っても動かない)
- X2/X3という新しい失敗モードを買ってまで今やる必要があるかを、
  ユーザーに判断してもらう

というのが誠実な扱いである。**個人的な推奨は「今は入れない」**
——施策Cの設計が(α)/(β)に変わればロック競合の形も変わりうるので、
Cの形が確定してから改めて必要性を評価するほうが手戻りが少ない。

## 3. その他の指摘

### 3.1 Y3(Medium): ゲートは断中のリモートSSHログインを増やす

ゲートで弾かれたタブは、それぞれ**独立したプロセス**で直接接続を試みる。
`drive_connect_recovery`の`RedeployGate`(`reconnect_backoff.rs`)は
**プロセスごとに独立**なので、断の最中に開いたタブの数だけ
「ダイヤル失敗 → サイレント再デプロイ」の試行が並行に走りうる。

実インシデントでも08:46:47に1回発火しているが、
ゲート導入後は「断中に開いたタブ数」ぶん発火する可能性がある。
リモート側のSSHログインが増えるだけで壊れはしないが、
**§5.3(新しい層に同種の問題を持ち込まないか)に1行足す価値がある**
——特に(γ)(無条件`Rejected`)を選ぶ場合。

### 3.2 Y4(Medium): 元の苦情は「遅い」ではなく「見えない」だった

§1.2③はこう書いている:

> ユーザーのwrapperは診断のため`--isekai-log-file`を常時指定している
> ため、上記①②の約2分半、**端末には文字通り何も表示されなかった**。
> これは「遅い」こと自体とは独立に、**「本当に動いているのか、それとも
> ハングしているのか分からない」**という体感速度の悪化を生んでいた。

そしてユーザーの報告は「ログインできない」→ 実際は
**「すごく遅かったけどつながった」**だった。

つまり**一次的な苦情は不可視性であり、接続失敗ではない**。
この観点で施策を並べ直すと:

- **§3.4(Win32進捗表示)**: 不可視性に直接答える。**muxの成功経路を
  一切捨てない**。
- **施策C(α)(情報フレーム)**: 同じ情報を、推測ではなく
  輸送層の実データとして進捗表示に供給する。
- **施策C(γ)(無条件`Rejected`)**: 不可視性は解消するが、
  ケース1でmuxの成功を捨てる。

⇒ **§3.4 +施策C(α)の組み合わせが、元の苦情に対して最も素直**である。
§7の実装順序で§3.4が最後(手順5)に置かれているのは、
元の問題設定からするとむしろ逆である可能性が高い。
少なくとも**「§3.4を先に出して、それだけでユーザーの体感が
どう変わるかを確認する」という選択肢**をADRに記録しておく価値がある。

### 3.3 Y5(Low): `Rejected`の文言

ゲート(あるいは(β))を採る場合、クライアントに出る文言は
「輸送層が再接続中」で終わらせず、**「このタブは直接接続で続行します。
多重化は次回以降の接続で自動的に戻ります」**まで書くこと。
そうしないと、ユーザーは多重化が恒久的に壊れたと誤解する
(既知の`isekai-ssh doctor`でも確認できない状態なので、
サポートコストになりうる)。
