## 1. AA1(Medium): 「候補ダイヤル」は包める対象ではない

### 1.1 事実

§3.1適用箇所2は、ティッカーの適用先として
「`connect_and_authenticate`(認証)・`wrapper.rs::bootstrap_and_register`
(再デプロイ)・**候補ダイヤル**の各長時間ブロッキング待ち」を挙げている。
しかし**候補ダイヤル(QUIC候補レース/STUN)は`isekai-pipe connect`
子プロセスの中で起きる**:

- `connect_attempt`(`connect.rs:657`)が`spawn_isekai_pipe_connect`で
  子を起こす。QUICのダイヤルはその子が行う。
- 親(`isekai-ssh`)は続けて`establish_over_stream`を呼び、
  **子のstdio越しにSSHのバナー/鍵交換が返ってくるのを待つ**。

⇒ 親から見ると、ダイヤルに要した時間は**`establish_over_stream`の
待ち時間に畳み込まれており、独立したawaitとしては存在しない**。

そして`establish_over_stream`は、Z2で除外した4種のうちの**1番
(ホスト鍵TOFUの`[y/N]`、`check_server_key`→`verifier.verify()`)を
内包する**。したがってZ2の方針(「そもそも対話を含まないawaitだけを
包む」)を厳密に守ると、**`establish_over_stream`は包めない**。

### 1.2 帰結: 適用箇所2の実効カバー範囲

Z2の制限を適用した後、適用箇所2が実際に包めるのは:

| サイト | 包めるか | 備考 |
|---|---|---|
| `authenticate_session`単体 | ✅ | 対話を含まない(`russh-stream-session/src/lib.rs:464-494`)。**実インシデントの72秒はここ**なので、一次目的は達成される |
| 再デプロイ中のSSH往復 | △ | `bootstrap_and_register`経由の再デプロイも、ブートストラップ先のホスト鍵が未知ならTOFUプロンプトを出しうる(`always-connects.md`の「Silentでも host-key TOFU は別」)。**対話を含まない区間だけに絞る必要がある** |
| 候補ダイヤル | ❌ | 子プロセス内。親側の等価物は`establish_over_stream`だが、TOFUを内包するため除外対象 |

**§1.1の内訳で言えば、ダイヤルの16秒は可視化されない。**
なお前景経路でも、この区間に端末へ出るものは無い——子のenv_logger出力は
`resolve_pipe_log_file`により**常にファイル**へ向けられ
(`child_stdio.rs`のdoc: native経路では「every case」で設定する)、
`print_reconnect_status`はresumeループ(=データポンプ確立後)でしか
呼ばれないためである。

### 1.3 推奨する対応

- **(推奨)正直にスコープを直す**: 適用箇所2のサイト一覧から
  「候補ダイヤル」を外し、**`authenticate_session`と、再デプロイのうち
  対話を含まない区間**に限定する。§1.1の内訳表で「ダイヤル16秒」は
  引き続き**ログのみ**(§3.4)でカバーされる、と明記する。
  これでADRの記述と実装可能な範囲が一致する。
- **(選択肢として記録)プロンプト側に停止を持たせる**: どうしても
  `establish_over_stream`区間(=ダイヤル+ハンドシェイク)を
  可視化したい場合は、ティッカーを止める責務を**プロンプトそのもの**に
  持たせる(`prompt_new_host_confirmation`/`prompt_passphrase`/
  keyboard-interactive/agentの各入口で`TickerSuspendGuard`を取る)。
  Z2が避けたかったのは「包むawaitを選び損ねる」失敗モードだが、
  この形なら**停止するのはプロンプト自身**なので、
  「プロンプトを足したのに停止を書き忘れる」以外の漏れ方が無い。
  ただし今回のスコープでは不要(72秒が本命であり、そこは
  `authenticate_session`で足りる)ので、**将来の拡張候補として§8に
  記録するに留めるのが妥当**。

## 2. AA2(Low): `busy_since_ms`のセンチネルと`Ordering`

§3.2のコード片:

```rust
/// ロックを保持し始めた時刻(モノトニック起点からの経過ms)。
/// 0 は「誰も保持していない」。
busy_since_ms: AtomicU64,
```

- **センチネルの曖昧さ**: モノトニック起点から1ms以内に取得した
  ロックは経過msが`0`になり、「誰も保持していない」と区別できない。
  起点はプロセス起動時(あるいは`GatedHandle`生成時)なので、
  holderの起動直後に最初のクライアントが来る経路は**実際に起こりうる**
  (`WARMUP_GRACE`が30秒ある理由がまさにそれ)。
  影響は「最初の1msに取得したロックについてゲートが素通しする」だけで
  実害は小さいが、**`elapsed_ms + 1`を格納する**か
  **`u64::MAX`を「保持していない」のセンチネルにする**と曖昧さが消える。
- **`Ordering`の指定**: 値は助言的(advisory)で、他のメモリ操作との
  同期には使わないので`Relaxed`で足りる。ADRのコード片に
  一言添えておくと、実装時に`SeqCst`を反射的に選んで
  「なぜここだけ強いのか」が後から分からなくなるのを防げる
  (既存の`active_clients`が`SeqCst`を使っているので、
  そちらに引きずられやすい)。

## 3. AA3(Low): §6(a)のテストは`advance`を刻む必要がありうる

既存テスト(`client.rs:593`付近)は
`tokio::time::advance(HELLO_ACK_TIMEOUT + Duration::from_secs(1))`で
**一括31秒**進めて、無応答オーナーが`Rejected`に落ちることを確認している。

適用箇所1を「1秒ティック付きの`select!`」に変えると、
実装が**毎ティックごとに新しい`sleep(1s)`を張り直すループ**になる場合、
一括で31秒進めてもループは1〜2回しか回らない(次の`sleep`が
張られるのは、タスクがポーリングされた後のため)。テストが
「30回ティックした」ことを確認したいなら**1秒ずつ刻んで進める**か、
実装側で`tokio::time::interval`(取りこぼしたティックを
`MissedTickBehavior`で扱える)を使う必要がある。

どちらを採るかを§6(a)かコード方針に一言書いておくと、
実装時に「テストが固まる/期待通り出ない」で時間を溶かさずに済む。
なお最終的な`Rejected`への到達自体は一括`advance`でも変わらないので、
**既存テストの回帰にはならない**——追加するアサーション側の話である。

## 6. 参考: 本ADRが辿り着いた設計の要約(記録として)

10ラウンドに及ぶレビューを経て残った設計は、次の2点に集約される:

1. **可視化は、各プロセスが自分の待ち時間を自分で測って表示する**
   ——プロセス境界を越えず、表示機構も新設せず、接続の挙動を変えない。
   したがって「効かなかった」というリスクが構造的に存在しない。
2. **待ちの短縮は、オーナーがローカルで確実に知っている事実
   (ロック保持時間)だけを使い、クライアント自身の既存の待ち方針
   (`HELLO_ACK_TIMEOUT`)を超えている場合に限って行う**
   ——短い断を悪化させず、新しい定数も新しいプロセス間プロトコルも
   導入しない。

途中で検討して捨てたもの(keepaliveチューニング、オーナー側会計機構、
`Mutex`→`RwLock`化、輸送層状態ファイル+入場ゲート、子stderrの中継)は
いずれも、**「他者の状態を推測する」か「閾値で待ちを打ち切る」か
「プロセス境界を新しく越える」のいずれかを含んでいた**。
現在の設計はその3つをすべて避けている——この共通項は、
将来この領域に手を入れる人にとって最も価値のある教訓なので、
§8か§1.6の末尾に1〜2行で残しておくことを勧める。
