# 大量のworktreeエージェントを並列運用する際の注意点

大規模な並列クリーンアップ・リファクタ作業(6並列レビュー→統合計画→
Sonnet/Opus並列実行→段階的マージ、のような形)では、多数のworktreeエージェントが
互いに独立した文脈で動く。ここで実際に踏んだ2種類の落とし穴と対処法を記録する。

## ルール

### 1. ベースブランチの確認を各エージェントの最初のステップとして必須化する

Agent toolでworktree isolationを使う際、意図したベースブランチ(例: 複数レーンの
成果を統合していく中間ブランチ)ではなく`main`など古いコミットから分岐している
ことがある(タイミング依存、原因未特定)。

- エージェントへの指示文には「作業開始前に、意図したベースブランチが自分のHEADの
  祖先であることを確認せよ(`git merge-base --is-ancestor <intended-base> HEAD`)。
  そうでなければ`git reset --hard <intended-base>`または
  `git merge --ff-only <intended-base>`してから作業を始めよ」という一文を必ず含める。
- それでもなお古いベースのまま報告してくるエージェントが出うる前提で、マージ側
  (統合ブランチを管理するセッション)は`git merge --no-commit --no-ff`で一旦結果を
  確認してからコミットする(後述、コンフリクト解決の前段確認として)。

**実例**(2026-08-09、Phase 2〜4の並列実行): 4ユニット(R4, M2→M1, T4, R6)中3つ
(R4, M2→M1, T4)は自力でベースの古さに気づき、fast-forward/resetして対処した
うえで報告してきた。1つ(R6)は対処せずそのまま完了報告してきたため、統合ブランチ
へのマージ時に手動コンフリクト解決(既に他レーンで削除済みのファイル
`tmux_scrollback.rs`のmodify/delete衝突、`orchestrator.rs`内2箇所のテストコード
コンフリクト)が必要になった。

### 2. build-checkフックの通知を鵜呑みにせず、まず自分の`git diff`を確認する

build-checkフックのエラー通知は、別のworktreeの状態や、報告元エージェント自身の
編集途中の一時的な状態を指していることがある。エラーが出るたびに即座に「バグだ」
と決めつけると、無関係な調査に時間を浪費する。

- エラー通知を受けたら、まず該当worktreeで`git diff -- <該当ファイル>`を実行し、
  自分(またはそのエージェント)の変更が実際にそのファイルに触れているかを機械的に
  確認してから調査の深さを決める。
- 「よく見る既知の空振りパターン」を意識しておく:
  - `isekai-ssh/src/native/`配下がLinux上でビルドすると丸ごと`dead_code`警告に
    なるのは正常(`native/mod.rs`のモジュールdoc参照——全プラットフォームで
    ビルド・テストされるが、実際に呼ばれるのは`cfg(windows)`時のみ)。
    「配線が切れたバグでは」と誤診断しやすいので注意。
  - (2026-08-10追記)`quicmux/src/mux.rs`のnon-exhaustive-matchエラー(feature無し
    単体ビルドで`AnyMux*`系enumが空になって起きていた既存の技術的負債)は
    `quicmux/Cargo.toml`の`default = ["noq"]`追加と、下記4番のhook書き直しの
    両方で恒久対処済み。**今後この特定のエラーは出ないはず**——出た場合は
    「既知の空振り」ではなく本当の regression の可能性が高いので、通常通り調査する。

### 3. マージ時は`--no-commit --no-ff`で一旦確認してからコミットする

古いベースから分岐したエージェントの成果(上記1番)や、大きく書き換わった
ファイル(SSOT強化・行シフト統合のような大規模リファクタの対象ファイル)を
マージする際は、`git merge --no-commit --no-ff <branch>`で一旦結果を
ワーキングツリーに展開し、コンフリクトの有無・自動マージされた箇所の妥当性を
確認してからコミットする。3-way mergeは「賢く」自動マージしてしまうことがあり、
特に大規模書き換え直後のファイルでは自動マージの結果を無条件に信用しない。

**実例**: R6のマージで`tmux_scrollback.rs`のmodify/delete衝突と
`orchestrator.rs`内2箇所のコンフリクトが検出された。前者は「他レーンで
既に削除済みのファイルをR6が古いベースの上で編集していた」ため、削除側を
採用。後者は「R6が追加した`reconnect_test_state()`ヘルパー関数自体は他の
変更と無衝突でauto-merge済みだったので、コンフリクト箇所ではそれを呼ぶだけで
良い」と判断して解決した——このように、コンフリクトの片側が「既にauto-merge
された別の関数定義を単に呼び出すだけ」であるケースは多く、丁寧に周辺を
読めば安全に解決できることが多い。

### 4. この種のツール(hook/CIスクリプト)は「単体ビルド」ではなく「ワークスペース
   マニフェスト起点」で書く

上記の`quicmux`の空振りは、`.claude/hooks/cargo_check_on_edit.py`(旧
`cargo-check-on-edit.sh`)が編集されたファイルの**属するクレート自身**の
Cargo.tomlを`--manifest-path`に渡していたことが直接の原因だった。ワークスペース
の他クレートがそのクレートに要求しているfeatureを一切継承しないため、
「実際のビルドでは絶対に踏まない」featureの組み合わせでビルドしてしまい、
偽陽性のコンパイルエラーを生む。

- rust-coreクレートを対象にした診断ツール・hook・CIステップを新しく書くときは、
  必ず対象クレートの**属するワークスペース**のCargo.toml(親ディレクトリを
  遡って見つかる、直下に`[workspace]`を持つ方)を`--manifest-path`に渡し、
  `-p <crate-name>`で対象クレートを絞る形にする。クレート自身のCargo.toml
  を直接使うのは、そのクレートが本当に独立したworkspace root
  (`noq-multipath-spike/`のような)である場合だけにする。

## 理由

worktree並列作業は各エージェントが独立した文脈で動くため、「自分のブランチが
本当に意図した状態から始まっているか」を誰も検証しない限りズレたまま進んで
しまう。同様に、build-checkフックは複数worktreeを横断して発火しうるため、
通知の内容だけを見て「自分(このworktree)の変更が原因だ」と決め打ちすると
誤診断・時間浪費につながる。マージ時の自動解決も、複雑な3-way mergeでは
盲信すべきではない。どれも「まず機械的に確認してから動く」ことで防げる。

## 参照実装

  `git merge --no-commit --no-ff <branch>`というコマンド自体

- `.claude/hooks/cargo_check_on_edit.py`(恒久対処その2——ワークスペース
  マニフェスト起点でのビルドに書き直したPython製hook。旧`cargo-check-on-edit.sh`
  からの書き直し理由はスクリプト冒頭のdocstring参照)
